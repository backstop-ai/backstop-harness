01 / THE SHIFT

Not less rigor.
Better timing.

The current insight came from watching the agent work: it explored freely, captured real gaps as issues, created plans when execution became concrete, delegated the work, and still ran the gates.

Pipeline-first

Structure before understanding

Force every conversation through bundle, spec, and plan ceremony before the shape of the problem is even known. The workflow is rigorous, but the entry cost breaks momentum.

Ambient orchestration

Structure at commitment

Let investigation breathe. When a durable requirement, defect, decision, or commitment appears, capture it through a typed boundary and let the runtime enforce the rest.

Explore without ceremony
Commit through typed transitions
Complete only with evidence

04 / THE LIFECYCLE

The lifecycle,
plainly.

Product commitments take the full path. Concrete defects take the shorter reactive path. Both converge on runtime verification and structured review before completion.

Product work

From exploration to delivered requirement

Explore>Bundle>Approve>Directive>Spec>Plan>Implement>Verify>Review>Complete
Reactive work

From concrete defect to proven repair

Explore>Issue>Plan>Implement>Verify>Review>Complete

Every authored artifact has a review loop

Draft > Validate > Review > Approve, or revise and repeat.

Every implementation has an evidence loop

Task > Runtime gate > Review > Complete, or repair and rerun.

    09 / GUARDRAILS

    Preserve the lessons.
    Retire the scaffolding.

    The original runtime remains a reference corpus. The new fork selectively rehydrates proven invariants while refusing accidental complexity.

    Keep as non-negotiable

    1. Typed lifecycle states and legal transitions
    2. Requirements, claims, tasks, tests, and evidence linked end to end
    3. Runtime-owned verification and final-evidence policy
    4. Durable pause, cancel, retry, and late-result suppression
    5. Structured writer and reviewer outcomes
    6. Explicit authority and conflict reconciliation

    Do not port literally

    1. Synthetic user messages for automatic handoffs
    2. Global target-directory state
    3. Regex inference of identity, evidence, or reviewer intent
    4. Stringly lifecycle states and timestamp-only freshness
    5. GET requests with mutation or dispatch side effects
    6. Agent prose accepted as verification

    Recommended starting position

    Build the spine, not the whole skeleton.

    Start with one reactive issue flow on native OpenCode V2. Let EventV2 own lifecycle history. Keep the Go Backstop engine canonical. Add child-agent execution only after the first typed boundary survives replay.

    • Native V2 for new behavior
    • EventV2 as lifecycle log
    • Go engine stays canonical
    • Issue -> plan is the first path
